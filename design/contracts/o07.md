## 1. Server truth used by the screens

### `readCaseMatches({ id, locale, pageSize, cursor?, briefRevision? })`

`briefRevision` is required with `cursor`. The read returns one of two shapes:

- `{ status: "criteria_required", caseId, caseVersion, brief: { id, revision, clientAcknowledgedAt } | null, reason: "missing_or_invalid" | "kind_mismatch" }`
  - `missing_or_invalid`: there is no brief revision, or its structured criteria do not parse.
  - `kind_mismatch`: `criteria.purpose` is not the deal's purpose (a buyer deal needs `sale`, a tenant deal needs `long_term_rent`).
- `{ status: "ready", caseId, caseVersion, brief, criteria, confirmed[], needsConfirmation[], count: { value, type: "exact" | "estimated" }, nextCursor | null, queryId, sourceTimestamp, stale }`
  - `confirmed[]` holds the items with `match = "match"`.
  - `needsConfirmation[]` holds the items with `match = "needs_confirmation"`. Each of these carries `unconfirmed[]`, the criteria keys whose value is not known.
  - Every item is a listing card (`reference, title, price, place, bedrooms, area, availability, manifestId, cover`) plus `unconfirmed[]` and `existingInterestId | null`.
  - `stale = true` means the published inventory changed since the first page (or a listing left between the two reads). The UI offers a refresh, never a snapshot.

### `readCaseCandidate({ id, reference, locale, briefRevision })`

Returns `{ caseId, caseVersion, briefRevision, candidate, match: "match" | "needs_confirmation" | "no_match", violated[], unconfirmed[], existingInterestId | null, sourceTimestamp }`.

- When anything is violated, `unconfirmed` comes back empty (filters.ts returns early).
- Errors: `version_conflict` (the brief revision changed), `validation_failed { briefRevision: ["criteria_required"] }`, `listing_unavailable`, `not_found`.

### `addInterest({ id, expectedVersion, operationId, reference, explanation, matchReview })`

This is the existing idempotent command.

- `explanation` is 3–1500 characters and is shown to the client as the fit explanation.
- `matchReview = { briefRevision, manifestId, availability, violated[], unconfirmed[], reviewed: true }`, copied from the candidate read the broker reviewed.
- Readback: `{ id, reference, interestId, version, recordedAt }`.
- A replay of the same `operationId` returns the recorded readback. If an interest for the same listing already exists, the command returns that `interestId` and adds nothing. A second press is harmless.
- Errors: `version_conflict { current: { briefRevision, manifestId, availability, violated?, unconfirmed? } }`, `listing_unavailable`, `transition_denied` (the deal is not active), `validation_failed` (`case_kind_mismatch`, `required_for_structured_brief`, `alternative_reason_required`, `criteria_required`), `not_found`.

### Criteria keys and their plain words

The same words appear in the requirement summary, in the «Потвърдено» and «Не е известно» lines and in the check cards.

| Key | bg word (`staff.matching.fact.*`) |
|---|---|
| `purpose` | «покупка» (`sale`) · «наем» (`long_term_rent`) |
| `propertyType` | property type label, for example «апартамент» |
| `place` | place name, for example «Сандански» |
| `availability` | «наличност» |
| `price` | «цена до {max}» · «цена от {min} до {max}» |
| `bedrooms` · `rooms` | «спални» · «стаи» |
| `area.<basis>` | «площ» (обща · застроена · жилищна · парцел) |
| `feature.<key>` | feature label, for example `feature.elevator` → «асансьор» |

Confirmed facts per item are derived in the UI: the applied `criteria` keys minus `unconfirmed[]`. The server does not list the matched keys (open question 2).

### Rules

- Unknowns and hard failures come first. A row lists «Не е известно: …» before «Потвърдено: …». A check lists «Не отговаря на» or «Трябва да се потвърди» before «Отговаря на» and before any way forward.
- No private requirement prose reaches the client. The explanation is about the property only, and the frame says so under the field. Butler drafts of the explanation follow the same rule. The `case.interest_added` event carries only keys (`violated`, `unconfirmed`), never the requirement text.
- An «explicit alternative» (adding a property that does not match) is not built. The screen shows one plain line and no button for it.
- Adding sends once. The button states its effect and limit next to it, and a second press adds nothing.

## 5. Entry, prototype paths and Butler

- **Entry.** On O07 (design 14:837 · 14:4650, proto 63:15763 · 66:47343), the requirement button «Прегледайте текущия вариант» used to point at O06 «Лице или организация». It is now «Вижте подходящите имоти» → O07READY. The W05-T4 path (O07 › O32MATCH › O07) is unchanged.
- **Prototype walks.** All of these pass on D and M:
  - O07 › READY › CHECKMATCH › ADDSEND › (1.5 s) ADDED › CHECKNEEDS › O14.
  - READY › CHECKNEEDS.
  - STALE › READY.
  - ADDOFFLINE › ADDSEND.
  - ADDUNKNOWN › ADDED.
  - ADDCONFLICT › CHECKMATCH.
- **Data variants.** CRITMISSING, CRITKIND, EMPTY, STALE, NEEDSCONF, CHECKNOMATCH, ONLIST and the add errors are data variants with no inbound click. They are not on @INDEX_STAFF (left alone during the parallel W03 round).
- **Proposed G1 task for W05.** «Add a property that fully matches to Alex's list.» Path: O07 › «Вижте подходящите имоти» › O07READY › «Проверете и добавете №912» › O07CHECKMATCH › «Добавете №912 в списъка на клиента» › O07ADDED. That is 3 taps plus the timed send; the explanation is pre-filled.
- **Butler.** Desktop uses the rail item «Butler» → XBUTLER (63:30796). Mobile uses the «Butler» chip in the context bar → XBUTLER (66:60456) on every O07 state frame. Butler may draft the explanation (a draft, property facts only). It never adds a property, confirms a fact or decides an alternative; the broker presses «Добавете …».

## 7. Open server questions

1. **Stale against the requirements.** `stale` covers inventory changes only. A requirements change after the list was read surfaces only as `version_conflict` on the next cursor read or candidate read. The UI shows O07STALE for both. Should the first-page read (or a light check) also say «results are older than the requirements», for example by comparing `brief.revision` at render time?
2. **Confirmed facts per item.** Items carry `unconfirmed[]` but not the matched keys, so the UI derives «Потвърдено» as the applied `criteria` keys minus `unconfirmed`. Is that safe, and is `availability` always one of the keys?
3. **Unknowns next to a failure.** `evaluateListing` returns `unconfirmed: []` once something is violated, so O07CHECKNOMATCH can list only the failures and says the rest is not fully checked. Should `readCaseCandidate` return the unknowns as well?
4. **Adding with unknown facts.** `addInterest` accepts `matchReview.unconfirmed`. The design asks the broker to confirm first and offers no add on O07CHECKNEEDS. If adding with unknown facts is allowed, the frame gains a Secondary «Добавете с непотвърдена наличност» and an effect line saying what the client sees.
5. **Explicit alternative.** The server already accepts `violated[]` with a reason of at least 20 characters (`alternative_reason_required`). Per the coordinator, the revision-bound decision is not built, so the UI shows only the plain line. Which command and fields will carry the decision?
6. **What a conflict carries.** `version_conflict` on add carries `current { briefRevision, manifestId, availability, violated?, unconfirmed? }` with no actor or time, so O07ADDCONFLICT names only what changed. Confirm this, or add `changedAt`.
7. **Undrawn outcomes.** `listing_unavailable`, `transition_denied` and `not_found` (add and candidate read) have no frames. Proposed copy: «Обявата вече не е публикувана. Имотът не е добавен.» or «Сделката не е активна. Имотът не е добавен.», with «Към списъка с имоти» as the one primary. Draw them?
8. **Same-request check.** After an unknown outcome, «Проверете същата заявка» replays the same `operationId`. Confirm that the replay always returns the recorded readback (or the existing `interestId`) and never adds twice. If it can return "still running", the frame stays and offers the check again.
9. **Opening a saved property.** `existingInterestId` has no route of its own. The link goes to the deal page (O05). Is there a stable anchor for one interest, for example the deal route plus `#interest-{interestId}`?
10. **Staff requirements editor.** `reviseBrief` has no staff frame. The criteria-required primaries open the deal's «Какво търси клиентът» section on O05, which only links back to O07. A staff requirements form is a design gap for the next round.
