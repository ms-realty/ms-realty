## 1. W03 handover · receiver side (Никол)

Command family: `handoverTask` (`src/server/work/handover.ts`). Agreed with Codex (C-03, server answers of the W03 fix round):

- **A. Receiver accept.** Only the receiver may call it. Fields: `nextAction` (text, required), `dueAt` (required, must be in the future, no default). No reason. Bound to the request version. `nextAction` becomes the title of the receiver's task; `dueAt` is a review time (on a waiting task it sets the follow-up time; a deadline promised to the client never moves). The UI labels it as a review time, never as an appointment or a client message.
- **B. Receiver decline.** Only the receiver may call it. Field: `reason` (required). Owner and promises stay unchanged.
- **C. Sender cancel.** Only the sender may call it. Field: `reason` (required). It stays distinct from decline.
- **Readback.** Each command returns the task id, version and `recordedAt` (UTC) only. There is no human receipt number: screens show the acting person and the time with the named zone, for example «Никол · 5 октомври 2026, 18:05 · Europe/Sofia».
- **Latest decision projection.** One `latestDecision: { kind: "declined" | "cancelled", actorName, reason, at }` for both participants: the sender's views (O23HPD, O23HPX) and the receiver's view of a cancel (O23HRX). Screens show `actorName` (status and «Записано» row), `reason` and `at` with the named zone; `kind` picks the screen.
- **No notifications.** No staff notification is delivered for handover steps. Screens never claim «… е уведомена» or «изпратихме известие»; they show only the visible decision readback. Clients receive no message for any handover step.
- **No absence link.** The request carries no absence record, so O23HR names only the sender.

Field to UI mapping: «Вашата следваща стъпка *» → `nextAction` (shown back as «Ваша задача»); «Кога ще прегледате отново? *» → `dueAt`; «Причина за отказа *» → `reason` (B); «Причина *» on O23HPC → `reason` (C).

Until A succeeds, ownership stays with the sender.

## 3. P12 · Inquiry receipt names the saved property

Read: `readInquiryReceipt` → receipt DTO. Per listing item (`listing`, or each item of `selectedListings` in the saved order): `{ reference, title | null, locale | null, sourceUrl | null, publicNow: true | false | null }`.

- `title` is the name saved at submission and is never re-read from today's listing.
- `publicNow` is read from the current publication only. No other live facts are shown: no price, area or availability.

The receipt header, number, owner line and «Какво следва» row are unchanged (`server.receipt.inquiryIntake.accepted.*`). The old price/area facts line is hidden because the DTO does not carry it.

## 4. Server questions

Answered by Codex (binding):

1. Handover readbacks return only the task id, version and `recordedAt`. No human receipt number: the frames show the person and the time with the named zone (sections 1–2).
2. One `latestDecision {kind, actorName, reason, at}` serves both participants, including the receiver's view of a sender cancel (O23HRX).
3. The request has no absence link: «отсъства от 12 до 16 октомври» is dropped from O23HR.
4. P12: `selectedListings` come in the order the visitor chose them; a multi-selection has `listing: null`.
5. P12VIEW: `purpose` distinguishes viewing requests, so the header can name the viewing request; no requested time is shown.
6. P12: `acceptedAt` is stored in UTC and displayed with the named zone (Europe/Sofia) in `{submittedAt}`.
