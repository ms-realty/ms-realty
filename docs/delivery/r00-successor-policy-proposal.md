# R00 successor release policy proposal

**Status: proposed; no launch gate is cleared.** This maps the legacy launch checks to the architecture in ADR 0002–0004. The sole acceptance verdict remains in [docs/acceptance.md](../acceptance.md); `production/data/launch-readiness.json` and `production/data/launch-input-checklist.md` stay the current launch authority until the agency owner and technical release owner approve a revision and the checks are regenerated from one evidence snapshot.

| Legacy check | Proposed successor proof at the exact release | Disposition |
| --- | --- | --- |
| Crawl inventory, redirect reviews, sitemap, structured data | Reconcile both domains against the final WordPress export, live crawl and released route map. Every historical URL has reviewed equivalent content, one-hop redirect or explicit removal approval; preserve sold listings and locales. Validate deployed status, canonical and metadata. | Retain; old passes do not qualify the rebuild. |
| Listing quality review | One complete human CSV covering each in-scope listing and its current facts, source, availability, media rights and publication decision. Source-as-is authorization does not assert factual or gallery review. Translations require separate human approval before indexing. | Retain and refresh. |
| Live Typesense/Meilisearch reports versus PostgreSQL search | The selected runtime is PostgreSQL 16.14. Require a redacted live sync/projection report, representative authorized search query report, failure/recovery evidence and deployed-path proof on the exact database and release. Retiring the external-engine report requirement requires explicit policy approval; a PostgreSQL fixture is insufficient. | Proposed replacement; conflict remains blocked until approved. |
| Hermes draft worker | Require live authenticated worker/provider reports, evaluated bounded draft tasks, budget and source-policy checks, and manual fallback. Hermes cannot publish, send, approve facts or make translations indexable. | Retain behavior and replace provider-specific evidence. |
| Payload runtime and admin identity | Require an exact-release report for first-party staff/client identity, grants, session boundaries, migrations, CMS/listing mutations, publication and worker leases. Exercise deny, revocation, restart and recovery paths against the deployed database. Payload package presence is not the outcome. | Proposed replacement; blocked until approved and proven. |
| R2 media coverage | Compare the complete released object manifest with the reviewed public gallery/media inventory; prove originals, rights, transforms and access controls from the deployed path. | Retain and recalculate. |
| Monitoring and rollback | Prove alerts, named responders, canary/disable/revert, queue and intake fallback, cache/URL behavior and a controlled rollback drill on the immutable candidate. | Retain. |
| Production recovery | Preserve encrypted independent off-site backup, isolated restore, checksums, rollback and named operator/reviewer approval. Preserve operator-authorized Ed25519-signed evidence until a separate approved successor changes it. | Retain. |
| Runtime smoke and app layer | Check all three hosts, gateway, web, worker and migrations by digest; bind browser and API journeys to the same release, configuration, schema, provider accounts and policy. Local fixtures are development evidence only. | Retain with successor components. |

The release manifest binds the exact Git and image digests, schema, URL/data/media manifests, provider and account references without secrets, role and policy revisions, checks and named approvals. Historical Search Console, Yandex Webmaster and backlink exports are optional analytics, never blockers. No old `pass` is carried forward to the successor merely because its name matches. R10–R12 require protected staging parity, authorized cutover, released-domain readback and a complete staffed operating cycle.

**Approval needed to activate this policy:** agency owner and technical release owner review the table, resolve the external-search and Payload substitutions explicitly, identify evidence owners and sign one revision-bound decision. Until then, source work and protected staging qualification may continue, while readiness stays blocked and no production route changes are authorized.
