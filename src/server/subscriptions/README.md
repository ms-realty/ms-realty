# Saved-search alerts (F05 / AT44)

This is an optional email service under exact subscriber consent. It never creates consent, sends marketing, or asks Butler to generate copy. The source of matches is the same parameterized PostgreSQL public search and approved current publication used by discovery.

`planSearchAlerts(pool, subscriptionId, {now?, rule?})` records an immutable `externalActions` email effect. Its payload pins the exact normalized criteria, subscriber version, verified contact/version, approved consent policy, human rule approval/hash, local calendar period and approved listing/revision/manifest/title/reference/link. A subscription row lock serializes competing planners. Empty matches create no email. Daily is the preference default; weekly uses a Monday-starting local calendar week. DST does not create extra periods. There is no promised delivery hour.

`dispatchSearchAlert(pool, provider, actionId, options?)` must receive the database pool, never an enclosing transaction. It commits `attempting` before provider I/O, then reacquires the current consent, contact, exact terms, rule approval/current decider grants and publication gates immediately before the bounded provider handoff. The gates remain locked through that handoff. A withdrawal that commits first stops delivery; an already-started provider handoff cannot be recalled. Changed or missing eligibility cancels the whole immutable digest. A later plan can use remaining eligible entries without rewriting an existing payload.

Provider acceptance records `acknowledged`; only authenticated delivery evidence records `verified`. A timeout records `outcome_unknown`. A process crash after the durable claim leaves `attempting`. Neither state is automatically replayed. A definite rejection may retry the exact same payload/key within 24 hours and the existing attempt limit. The application ledger continues to reserve listing/revision pairs after unknown, attempted, accepted, delivered or failed effects; cancelled pre-send effects release them. Definitive failures require explicit operator disposition rather than silently trying a new logical message. `lastSentAt` denotes provider acceptance for calendar scheduling, not proof of delivery.

The generic outbox routes `subjectType=search_alert_digest` to this guarded dispatcher. An alert template without that subject binding is refused. The existing ledger, generic safety sweep and authenticated delivery reconciliation remain authoritative; no second sent/delivered table or schema was introduced. `sweepSearchAlerts` returns a keyset `nextCursor`; the worker queues continuation so early empty subscriptions cannot starve later ones. Match scanning is bounded to 100 pages of 60 results per planning attempt, and each digest has at most 20 entries. `scanIncomplete` is retained and returned when the bound or an incomplete source is encountered; it is not a claim that every matching listing was examined. A search whose previously notified prefix reaches that scan bound requires narrowing or an operator follow-up, not a fabricated complete result.

Delivery is disabled unless `SEARCH_ALERTS_ENABLED=true` and `SEARCH_ALERTS_TEMPLATE_APPROVED=search-alerts.v1`. These environment gates alone confer no approval. A fresh human staff operator with both `settings.manage` and `message.send_external` must approve the exact fixed template, schedule and configured public/client origins at `/{locale}/operations/subscriptions`. The immutable rule snapshot/hash and mandatory expiry are stored in `approvals(kind=message_send)`. Current human status/grants, approval hash/expiry and the exact approval ID are checked for every dispatch. Reapproval invalidates the previous decision and queued work; disable does the same. The native form has a server-issued operation key, current-preview fence, durable private receipt and a bounded signed per-session draft cookie on error. Approval does not enable the environment gate or send test mail.

`renderSearchAlert` accepts only the fixed strict schema and own-origin canonical links. Output is plain text, with source line and bidi controls removed; no HTML, arbitrary subject/body, private notes, media or tracking is rendered. BG is primary and fixed interface text exists for all seven public locales; listing copy itself remains the approved current locale source. Separate purpose-specific terms currently remain subject to the approved-content locale policy.

Tests use a newly migrated disposable PostgreSQL database, synthetic approved source/consent/rule fixtures and `TestMessageProvider`. They cover concurrency, source and consent revocation, no-match behavior, calendar periods, immutable retry keys, unknown outcomes, approval authority and generic outbox routing. Fake acceptance is not live Resend or launch qualification. No production mail or live provider call is part of these tests.
